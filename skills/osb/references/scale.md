# Dependencies, scale and bounded operation

No executable dependency is required to read this skill. Runtime backend/client is an explicit setup choice, not bundled infrastructure. Prefer existing GitHub access for cooperative or validated CAS mode; prefer an existing compatible authority for enforced claims. If a new authority is justified, one small standard-library application plus core SQLite on one durable host is a V1 option. Existing SSH can carry authenticated commands if the deployed contract defines argument encoding and per-user authorization. Do not add Redis, Kafka, Kubernetes, a cloud account or another database solely for this workflow.

Capacity has not been measured. The following are initial safety ceilings for a future implementation review, not performance claims: 100 items/page, 64 KiB mutation payload, 1 MiB handover evidence as external private artifact rather than inline ledger content, 1,000 pending projection events per project, two mutation retries, and maximum 10 queued requests per principal. Reject excess with explicit busy/limit outcomes; never discard accepted operations. Limits are configurable by the human owner after measurement.

SQLite: one authoritative writer per database. Use short transactions, configured bounded busy timeout, foreign keys and appropriate durability; no external API calls while holding a write transaction. Index `(repo_id, team_id, task_id)`, active conflict keys, operation-key scope, generation/epoch and outbox cursor/status. Paginate audit reads with stable cursors; batch projection updates conservatively, preserving each operation's receipt. A hot shared database serializes writes even with WAL. Independent project databases can reduce contention, but cross-project claims then need an explicit coordinator or must remain unsupported.

GitHub CAS: one branch head serializes mutations; measure conflict/retry rate before increasing writers. Cache immutable commit content; always re-read current head for mutation. Shard independent project scopes only when no invariant crosses partitions. Batch compatible operations in one commit only if all validations and receipts are atomic. Avoid per-agent minute heartbeats in commits/issues. Milestone projections and owner-reviewed advisory TTL reduce noise, but do not provide timed locks. API limits/backpressure must be observed from actual responses; account limits are shared with other work ([GitHub rate-limit guidance](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)).

Outbox: retain event ID, authority version, attempts, next-attempt time and last redacted failure. Respect retry-after; bounded retries then paused/dead-letter state with owner-visible reconciliation. When queue reaches its ceiling, pause new mutations that require guaranteed eventual projection until drained, while keeping read/revoke available where feasible. Worker failures cannot roll back already committed authority state. Do not depend on webhook redelivery or ordering for correctness; deduplicate, persist and reconcile ([GitHub webhook failures](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)). Actions concurrency is scheduling with bounded queues, not a durable ledger or lease server ([Actions concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)).

Retention: policy must cover audit history, terminal tasks, operation receipts/tombstones and projection dedupe IDs. Archive summaries and evidence links; retain enough identity, epoch, generation and key digest to reject stale replay. If retention removes a retry key, reject it as indeterminate/too old rather than silently treating it as new. Backup restore increments epoch and requires explicit grants before work resumes.

Upgrade triggers: measured SQLite lock waits/errors, branch CAS conflict rates, projection backlog age, p95 mutation latency, restore time and access-isolation needs. Reuse the **implemented, versioned** contract through adapter mapping when changing storage. No default Postgres migration or multi-region design; introduce shared transactional storage only after measured need. Record tested capacity separately from estimates and keep merge/deploy enforcement boundaries visible.
