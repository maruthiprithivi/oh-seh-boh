# Setup and architecture choice

First inspect existing project instructions and ledger config. If a deployed authority already exists, use its documented version and map its semantics to this contract. Never infer compatibility from a similarly named command. An unmapped generation, authorization, or expiry rule blocks enforced mode. This package has no dependency on another project's unmerged implementation code.

Prepare `.coordination/ledger.json` from `../config/ledger.example.json` in the approved repository only after a destination decision. Before applying it, resolve host, repository numeric/node ID, team boundary, human primary owner and permitted delegates, exact issue destination, authentication route, service URL if any, and the operations each role may perform. A repository rename/transfer is acceptable only if authenticated resolution yields the same ID and its new access boundary is reviewed. A fork has another ID. Cross-repository work needs explicit per-repository scopes, not a wildcard.

| Mode | Suitable use | Authority | Availability and cost |
|---|---|---|---|
| GitHub cooperative | Small trusted team, human can serialize claims; no enforcement needed | Named human integration owner acknowledges grants on a designated control issue | Uses existing GitHub account and issue access; no separate service. Current account/Projects limits and pricing apply. Owner offline or ambiguous comments pause shared writes. |
| GitHub branch CAS | Low contention, compliant validated clients, no automatic timed takeover | Dedicated ledger branch; expected-head atomic commit | No extra service; GitHub API/commit limits and repository access apply. Requires a deterministic validator/client, not shipped here. Time and bypass limitations in [CAS design](github-cas.md). |
| Transactional service + GitHub projection | Concurrent users, stale agents, ownership must be rejected deterministically | Existing compatible service or separately reviewed implementation with durable transactions and fencing | Requires service/database operation, backups, identity setup and monitoring. Outage pauses mutations; visibility may lag. Hosting cost is provider/workload dependent, never assume free-tier availability. |

Recommend Issues for durable task intent and discussion, one control issue for team policy, and an optional Project for views of state, owner, lease expiry, and PR. Issues are inappropriate as exclusive lock authority or immutable audit storage: comments can be edited/deleted and multiple writers can race. GitHub Projects automations help presentation, not claim serialization ([GitHub documentation](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations)).

If Issues cannot be used because of privacy, repository policy, noise, or retention, keep the authoritative ledger in the transactional service and publish only redacted summaries to an approved private coordination repository or existing tracker. Decide visibility explicitly; do not replicate private task details into public issues. A branch containing JSON or a shared document can be a reviewable configuration store; do not treat it as a running lock service without a separately designed CAS protocol.

For cooperative setup, draft a control issue listing team scope, human owner, delegates, acknowledgment format, advisory lease policy, escalation contact and task issue template. Publish only with authorization for that target. For service setup, draft a capability mapping and deployment proposal; do not install a service, App, webhook, or grants merely to join. Start in read-only mode until identity, permissions, and authority capabilities are verified.

Permissions: separate read-only join/reconcile from issue-write projection and authority mutation roles. Scope GitHub credentials to selected repositories; issue-comment operations support fine-grained tokens with Issues permissions ([endpoint documentation](https://docs.github.com/en/rest/issues/comments)). Projects may require additional permissions; omit Projects if unneeded. Service identity must bind the human to authorized team/repository operations, not trust a principal string in JSON. Prefer individual short-lived credentials or an approved scoped broker; credentials are never shared between people through this ledger.

Setup review must record authority version, deterministic client/gate version (or manual-only limitation), retention, backup/recovery owner, revocation path, TTL/heartbeat policy, enforcement boundary, and migration procedure. Changing authority freezes new claims, inventories active grants, explicitly revokes or transfers them, increments authority epoch, and records a human-approved cutover. Never run both authorities for the same scope.
